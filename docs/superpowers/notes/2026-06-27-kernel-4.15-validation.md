## Kernel Choice and Rationale

**Target:** kernel 4.15 (production minimum).  
**No exact 4.15 image available.** The Cilium lvh kernel catalog (`lvh kernels catalog`) provides:

```
4.9, 4.19, 5.4, 5.10, 5.15, 6.0, 6.1, 6.3, 6.6, 6.12, 6.18
```

The internal registry (`gitlab.platinum-sec.com:5050/frontier/lvh/kernel-images`) was inaccessible due to auth restrictions (would have had `rhel8-main` = 4.18).

**Why 4.9 was rejected:**  
`BPF_MAP_TYPE_LRU_HASH` requires kernel ≥ 4.10. Testing on 4.9 would produce a FALSE NEGATIVE (map creation fails, not a verifier/attach issue). 4.9 does not represent the 4.15 target for our use case.

**Chosen kernel: 4.19-main → vmlinuz-4.19.325**  
- Nearest Cilium image ABOVE 4.15
- Post-LRU_HASH (≥ 4.10) ✓
- Post-clsact (≥ 4.5) ✓  
- Post-BPF TC classifier (≥ 3.18) ✓
- Verifier is nearly identical to 4.15 for raw-offset programs without BTF func annotations
- Acceptable proxy for the 4.15 target (verifier improvements between 4.15 and 4.19 are minor for `SCHED_CLS` programs of our complexity)

## Fixes Applied (Two Issues Found and Resolved)

### Fix 1: aya BTF/func_info incompatibility on kernels with btf_func=false

**Root cause:**  
On kernel 4.19.325, `is_btf_supported()` returns true (basic BTF type loading works), but `btf_func` is false. Aya then:
1. Sanitises the object's `.BTF` section (FUNC→TYPEDEF, FUNC_PROTO→ENUM substitutions)
2. Uploads the sanitised BTF to the kernel (succeeds)
3. Sets `prog_btf_fd` + `func_info` in BPF_PROG_LOAD

The kernel rejects BPF_PROG_LOAD because `func_info` type_ids now resolve to TYPEDEF (not FUNC) after sanitisation, returning EINVAL with an empty verifier log.

**Fix in `mymitm/src/bpf.rs`:**  
When `btf_func: false`, zero out the `.BTF` and `.BTF.ext` sections from the in-memory ELF bytes before passing to EbpfLoader (via new `strip_btf_sections()` helper using the `object` crate). This prevents aya from finding func_info at all. Since our object has **no CO-RE relocations**, stripping BTF is a no-op for correctness.

```rust
let btf_func_ok = aya::features().btf().map(|f| f.btf_func()).unwrap_or(false);
let obj_bytes = if !btf_func_ok {
    Cow::Owned(strip_btf_sections(EBPF_OBJ))
} else {
    Cow::Borrowed(EBPF_OBJ)
};
```

### Fix 2: UpstreamVal uninitialized padding — 4.19 verifier strict stack read

**Root cause:**  
`UpstreamVal { box_ip: u32, box_port: u16 }` has 2 bytes of implicit padding to reach size 8 (`#[repr(C)]`). When `cls_eth_egress` constructs `val` on the stack and passes it to `bpf_map_update_elem`, the 4.19 verifier detects an uninitialized read:

```
invalid indirect read from stack off -20+6 size 8
```

Newer kernels allow this; 4.19 is strict.

**Fix in `mymitm-common/src/lib.rs`:**  
Added explicit `_pad: u16` field to `UpstreamVal`:

```rust
pub struct UpstreamVal {
    pub box_ip: u32,
    pub box_port: u16,
    pub _pad: u16,   // explicit padding; must be initialised to 0
}
```

And in `mymitm-ebpf/src/main.rs`:
```rust
let val = UpstreamVal { box_ip: c.box_ip, box_port: m.src_port, _pad: 0 };
```

## Confidence Statement for the 4.15 Target

**HIGH confidence** that the programs will load and attach on a real kernel 4.15.x.

Rationale:
- Tested on 4.19.325, which shares the same BPF verifier generation as 4.15 for TC classifiers of this complexity (raw offset loads, basic map lookups, no helpers beyond `skb_load_bytes`, `l3_csum_replace`, `l4_csum_replace`, `map_lookup_elem`, `map_update_elem`)
- Both fixes address 4.x-era verifier strictness (btf_func detection covers all pre-4.18 kernels; explicit padding covers all 4.x kernels with strict stack-init checks)
- clsact qdisc support exists since 4.5 ✓; `BPF_MAP_TYPE_LRU_HASH` since 4.10 ✓; `direct-action` since 4.8 ✓
- The `btf_func_ok` detection uses `aya::features()` which probes the running kernel at startup, so it automatically adapts to any kernel ≥ 4.10 without version hardcoding
- The only theoretical gap: 4.15 vs 4.19 may differ in verifier complexity limits. Our programs are 183–228 instructions, well within historical 4.x limits (4096 insns for SCHED_CLS)

## Concerns

1. **No exact 4.15 image:** We tested on 4.19 as the nearest available proxy. An exact 4.15 image (or 4.14 RHEL) would provide stronger guarantees. The internal `rhel8-main` (4.18) image would be a slightly better proxy but was inaccessible.
2. **TUN interface not available in the 4.19 lvh kernel:** CONFIG_TUN not compiled into the lvh 4.19 image. Used veth for `mmtun0` which is functionally equivalent for TC attachment purposes.
3. **aya BTF behaviour is an upstream gap:** The FUNC→TYPEDEF sanitisation without clearing func_info is arguably an aya bug for kernels with `btf_func=false`. Filed as a note for future aya upgrades (the `strip_btf_sections` workaround is self-contained and safe).
